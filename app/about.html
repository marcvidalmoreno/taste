Why

I make images for my posts and wallpapers, and I know what I like when I see it. Over the years I saved about 1,000 wallpapers. An image model can't read that folder, but it can read a written description.

So this project turns the folder into words: styles with a palette, light, composition, medium, mood and, just as important, what to avoid. Then every image I make, and how I rate it, feeds back into those words. The taste is meant to grow from evidence, not from guesses.

The wallpapers belong to the people who made them. They stay on my laptop. Only the descriptions and the images I generate are mine to show.

History

  1. 8 Nov 2026 First version. Five styles found by clustering the wallpapers by colour, prompt packs for the Gemini app (Nano Banana), and an inbox that sorts newly liked images into a style.
  2. 13 Nov 2026 Codex route. Images made with ChatGPT through Codex CLI, on my plan, with no API key and no bill. One image per run, every run logged with its cost in allowance. Variations, contact sheets, ratings and a "distil" step that turns ratings into style edits.
  3. 13 Nov 2026 Taste rebuilt from zero. Colour alone found the right style only 36 % of the time. Every wallpaper was tagged by eye on contact sheets (subject, medium, mood, light) and grouped into fourteen styles, each approved one by one. Palettes are measured from the images.
  4. 13 Nov 2026 This web app. Look at a batch, mark keep / almost / no with a reason, save, start variations, see ratings per style.
  5. 14 Nov 2026 Gallery, Taste and About pages. Everything I've made in one place, and the styles shown with my own images as examples.

How it works

  1. Styles. Each style is one JSON file in taste/styles/. build_taste.py turns them into short prompt blocks in taste/taste.json.
  2. Generate. codex_run.py starts one fresh codex exec per image with a style and a subject. Native size is 1672 × 941, about a minute and ~95k tokens per image (mostly cached).
  3. Vary. variations.py changes one thing at a time: palette, subject, composition or mood. The seed goes in as a reference.
  4. Rate. In this app or with rate.py: keep, almost or no, with a short why.
  5. Distil. About every 20 ratings, distil.py sums up what the ratings say per style; Claude Code proposes edits to the style files, I approve each one, and the prompts are rebuilt.

The app is plain HTML, CSS (Pico.css) and JavaScript modules, served by a small Python server on 127.0.0.1 only. No framework, no build step. Images, ratings and logs stay in generated/codex/, which git ignores.

Decisions

Styles by eye, not by colour
Colour clustering was quick but wrong two times out of three. Tagging by eye took longer and gives styles I recognise as mine. Tools still offer a top-3 guess, and I confirm it.
Codex for images, Claude Code for the taste
One tool generates, the other one thinks. Codex never edits a style file; Claude Code never edits one without my OK. Files are the hand-off between them.
One change per variation
If a variation changes palette and subject at once, I can't tell which one I liked. One change, one lesson.
Draft, then save
Marks stay drafts until I save them. Saved ratings are read-only, because the distil step counts rows to know where it stopped.
Local first
The wallpapers and every reference image stay private. The app listens on this machine only.
Measure the allowance, don't guess it
Every run logs the allowance read from Codex's own log, so the budget (about 40 images a week) rests on numbers.

How we work

Three of us, each with a clear job:

  • Me: I look, rate and decide. Every style edit needs my OK.
  • Claude Code: owns the taste files, reads my ratings, proposes edits, builds the tools and this app, and writes a changelog entry with an undo line for every change.
  • Codex CLI: makes the images, one fresh run per image, and nothing else.

The rules for Claude Code are in the repo's CLAUDE.md: stop and report after one failed retry, ask before spending a large share of the allowance, check every push for private data.
